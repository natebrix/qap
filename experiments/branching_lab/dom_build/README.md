# dom_build: pair exchange dominance in the solver (`dom.pair`), Nov 19-20 2026

## Verdict

**Valid as implemented, on the evidence below; and it does on real subtrees what the replay said, or more.**
`dom.pair = 1` (default 0) drops a popped node, before any bound, when exchanging two of its fixed rows makes
every completion strictly cheaper. Evidence for validity:
- **Every QAPLIB instance up to n = 20 the solver closes in the time given ends at the optimum with the key
  on, with no open node, from an incumbent one above the optimum** (the search must find the optimum itself),
  and the 64 cheap ones also from **2 x optimum + 100**. That covers 86 instances (car, chr, els, esc08/16
  with up to 17,280 optima, had, law, lipa, nug with symmetry files, rou, scr, tai a and b), the test firing on
  77 of them. No wrong optimum, no open node, in 150 key-on runs [m].
- **Every node the solver dropped in 25 of those runs (37,420 nodes) was recomputed** by an independent general
  formula (no symmetry assumed, linear term included, original data) and, where there is no linear term, by the
  dominance study's `dom.py`: all > 0 and equal; **31,610 of them, those with at most 8 free rows (7 in the three largest runs), by brute
  force** over every completion: the brute-force max-min equals the solver's value and every completion costs
  more than the optimum [m]. The 188 nodes dropped in the tai35b whole tree and the tai35b, tho40 and tai60b subtrees below were
  recomputed with `dom.py` too: all >= 1 [m].
- **The solver's own code equals the replay's Python on every node of seven production traces** (373,216 nodes:
  tai60b, tai50b, tai50b-r9, tai40b, tai35b, tho40ab-32, nug30), value for value [m].
- **Key off, the node traces are identical to the unpatched build** (every field but CPU) on nug20 whole
  (476,889 lines), a tai35b subtree and a tho40 subtree with the production recipes [m]; the repo's
  regression check matches its reference exactly.

What it saves, measured (both arms with the patched build, the same subtree, the production recipe):

In each subtree the key-on tree is exactly the key-off tree less the subtrees under the dropped nodes (as sets
of fixes, every common node with the same outcome). On tai60b the local trees are bigger than the production
run's (a `-F` start has no parent DNN state or pool, so the bounds are weaker and the lines differ), and
the test removes correspondingly more: the dropped nodes are the same kind the replay named, children of a
chain node in which two chain rows have swapped columns.

Caveats, each explained below: (1) **with a poor starting incumbent the test can cost nodes** (had14 from
2 x optimum + 100: 3,668 nodes off, 9,940 on), because a dropped node may hold good, non-optimal solutions
that the key-off search would have used to improve its incumbent early; the replay's "a late incumbent saves
the same or more" is wrong in general. Production runs start one above the best known value, where this does
not arise. (2) Adding the key changes the settings hash of every run (the hash covers every policy entry,
defaults included): **a state file written by the current solver will not resume under the patched one without
`--allow-settings-change`** (as with the nine keys of Nov 17). (3) With the key on the solver writes state
version 10, which `bench/parallel.py` (and so the coordinator) mislabels as 9 and then cannot read back; a
one-line fix is in `parallel_state10.patch`, kept out of `dom_pair.patch` (see 6). (4) `make test` fails at
`estimate` on this loaded machine, on the CPU ratio only (see 5). (5) The dominance README's tho40ab-32 numbers
were computed on the wrong instance (see 4).

## 2. Design decisions

**Where.** `bnb()` in `latest/bnb.C`, right after the pop-time discard (outcome P) and before `pick_param`,
the enumeration of small nodes and any bound, for every node with two or more fixed rows. A dropped node
gets the trace outcome **X** and is counted in a new per-level counter `dom_f_level` (and, like P, in
`fathom` and `f_level` but not in the node counter: trace lines = node + popped + dropped). The run prints
`Pair exchange dominance: N nodes dropped` and a per-level table, only when the key is on. Testing at pop
covers every node, those restored from a state file included; children are not tested before `push`
(the optional part of the specification), so a dominated child still takes stack and state-file space
until it is popped.

**The setting.** One policy key, `dom.pair = 0|1`, default 0 (`latest/settings.C`, RUNNING.md's table
regenerated by `tests/settings_doc.py --update`, the eleven settings goldens regenerated with
`fullrun_dump`). It is read in `bnb()`, so it applies to the estimator's dives too.

**Which matrices.** The original data as `bnb()` holds them: `q->A`, `q->B`, `q->C` after
`symmetrize_QAP` (so both matrices are symmetric, one of them holding halves). Not the node's reduced
problem: `reduceQAP` folds the fixed rows into the reduced linear term and shift, and the test needs the
two fixed rows separately, so it cannot be read from the reduced problem at all. The symmetrised and the
original data give the same value: symmetrisation leaves every objective value unchanged, and Delta is a
difference of two objective values. Shown, not only argued: `cmp_replay.py` compares the solver's code
(`domcheck`, on the symmetrised doubles) with `dom.py` (the general formula with no symmetry assumed, on the
original integer data) on every node of seven traces, 371,617 nodes in all: equal on every node.

**Arithmetic.** Exact integers: the code works on 2A, 2B and 4C as 64-bit integers and sums in 128 bits, so it
computes 4 min Delta exactly, and the test is "4 min Delta > 0". That is the strict test with no tolerance
and no rounding, whatever the parity of the objective values.

**Non-integer data: off.** The test runs only if (a) `set_fathom_tolerance` found the original data integral
and exactly computable (DELTA > 0), (b) both matrices are symmetric after `symmetrize_QAP` (when neither
is, the solver already warns that its bounds are unreliable), and (c) every entry of 2A, 2B and 4C is an
integer below 2^31 (2^60 for C), so that no sum can overflow. Otherwise it never fires, and the run says so
once (`dom.pair: the test is off for this instance: ...`).

**Strict.** "> 0", never ">= 0". With ties allowed, two twins with Delta = 0 (esc08a's {0:0,1:1} and
{0:1,1:0}) would drop each other although both hold optima. On the esc16 instances (many optima, many ties)
the runs end at the optimum with the key on (table below).

**Symmetry reduction (re-derived; I agree with the dominance README).** The invariant a run keeps is
I: *the incumbent is optimal, or some open node's feasible set holds an optimal permutation.* Each operation
preserves I on its own, so any composition does:
- a bound fathom, a QPB child elimination (`branch()` creates no child whose predicted bound exceeds the
  cutoff) and an eliminated variable (PARTIAL rows) remove only completions of cost > incumbent - DELTA,
  hence >= the incumbent on the objective grid: if one of them was optimal, so is the incumbent;
- the J2/J3 symmetry reduction keeps, for any completion p of the node, a child holding g(p) with g an
  automorphism fixing the node's fixed locations, of equal cost; if the node held an optimum, a kept child
  holds an optimum;
- strict dominance removes a node only if every completion of its fixes has a strictly cheaper exchange
  image, i.e. a node whose feasible set (a subset of those completions) holds no optimum at all. It removes
  nothing I depends on, whatever the incumbent is, whether or not it is optimal.
So the two reductions compose in either order. The one thing that would break this is a tie-breaking
(non-strict) dominance, which needs its own total order and can disagree with the orbit representative the
symmetry reduction keeps. The test ignores the node's eliminated variables and minimises over all
completions of its fixes, a superset of its feasible set: conservative.

**What the proof claims afterwards.** Unchanged for the optimum: "the incumbent is optimal" and "no solution
below the cutoff" (the minimum lies in no dominated node). What is lost is any enumeration of *all* solutions
below a cutoff, which the solver does not claim.

**State files.** A run with `dom.pair = 1` writes `QAP-STATE 10`: version 9 plus a `dom_f_level` line after
`cut_t_level`. Every other run writes version 9, byte for byte as before, so readers of today's files are
untouched. The reader takes 1 to 10.

## 4. Savings [m]

`slices.sh` → `logs/slices.log`, `logs/slices/` (traces, `*.cmp` from `slice_cmp.py`). Both arms run with the
production recipe (`par/tai35b_*.par` = line_signals' tai35b.par, `par/tai60b_*.par` = the tai60b recipe,
`par/tho40_*.par` = tho40-ship32.par; the `_on` files add `dom.pair = 1`), single-threaded, the incumbent the
production run's. CPU is the solver's "Total Time"; the machine was shared (another agent's tai35b solve
throughout), so CPU differences below about 5% are noise.

**tai35b whole** (key on, one process, incumbent the optimum + 1; `logs/slices/tai35b.on.log`, `tai35b.cmp`):
closed at 283,315,445 with no open node, 909 bounded nodes + 74 dropped + 34 popped, 6,665 CPU s. The key-off
tree is line_signals' `tai35b_base` (the same recipe through the coordinator, 2 slots): 972 + 45 popped, 6,931 s.

- **The key-on tree is the key-off tree with 74 leaves dropped instead of bounded**: the same 1,017 fixes in
  both traces, and no key-off node lies under a dropped one. In the key-off run those 74 were 47 fathomed by
  the DNN bound, 22 by QPB and 5 popped; their bounds cost 52 s there (0.75% of the CPU), and 0.002 s with the
  key on. That is the replay's figure exactly. The 3.8% between the two arms' totals is noise (line_signals'
  two key-off runs differ by 7%), not a saving.
- The replay's 82 dominated nodes are these 74 and 8 that both runs popped when the incumbent arrived (a popped
  node is not tested). No node was dropped that the replay did not predict.
- Ten common nodes have another outcome: six at depth 20 that the key-off run popped and this one fathomed
  (QPB 4, DNN 2: the serial run met them before the incumbent), and four at depths 3 and 8 where the DNN
  bound was a little weaker here and the cut phase fathomed the node instead (warm starts and the pool
  depend on the order of the search). None branched in one run and not the other.
- All 74 recomputed by `dom.py`: min Delta >= 1, smallest 4,657.

So on tai35b the test removes no subtree: every dominated node is one the bound fathoms without children.
The saving is those bounds, under 1% of the CPU.


**tai35b depth-6 node** `19:26,18:12,23:5,26:6,27:34,30:14` (chosen: the cheapest tai35b subtree with drops):
off 85 nodes, 624 s; on 71 + 14 dropped, 577 s. The 14 dropped nodes are exactly the replay's 14 for this
subtree, all leaves; the local tree (85) is bigger than the production one (58) and contains all 58.

**tho40t depth-4 node** `26:10,8:0,16:32,2:8` (the identity slice): off 210, 521 s; on 196 + 14, 482 s. The
local tree shares only the root with the production one (a cold start picks other lines), so no node-for-node
comparison with the replay is possible; the replay's own count for the production subtree is also 14.

**tai60b path chain, depth 17** `44:45,...,3:36,11:39` (the cheapest tai60b subtree where the test removes
more than the leaves: production 44 nodes, 0.13 h, of which the replay drops 43). Locally the line chosen has
24 children instead of 43, and without the test one of them grows a chain to depth 21+: off 148 nodes,
1,807 s. With the test **all 24 children are dropped** at pop: 1 node + 24 dropped, 249 s (-86% CPU). The 24
are among the replay's 43; none is dropped that the replay did not flag.

**tai60b path chain, depth 14** `44:45,...,5:55,9:57` (production 179 nodes, 0.86 h; replay: 82 highest
dominated nodes, 169 nodes and 0.55 h under them). On: 16 nodes + 76 dropped, 713 s; 41 of the 76 are among
the replay's 82, the other 35 are children of nodes that branched on other lines locally. Off: stopped after
252 nodes and 1.15 CPU h of trace (my kill rule: it was descending a chain under one of the nodes the on arm
drops, and it held the queue for the tai35b run); everything it had done outside the dropped subtrees is in
the on tree with the same outcome, and 246 of its 252 nodes are under dropped nodes. So the saving here is
at least 236 nodes and 83% of CPU.

**Where they differ from the replay, and why.** The replay assumes the production tree; a `-F` subtree run
starts without the parent's DNN state and cut pool, gets weaker bounds and (rule 9, from the DNN marginals)
other lines. Where the local tree is the production tree plus extra nodes (tai35b), the dropped set equals the
replay's. Where the lines differ (tai60b, tho40), the test still drops the same kind of node, and on tai60b a
much larger share of the work, because the extra nodes the weak cold bounds create are themselves in
dominated subtrees. This says nothing about tai60b whole: the replay's 11.5% of CPU stays the only estimate
there, and it was computed on the production tree.

**Poor incumbents.** From 2 x optimum + 100 the key-on runs have more bounded nodes on 17 of 64 instances
(had14 2.7x, nug15 1.44x, car10gk 1.37x, had10 1.31x, rou12 1.29x, had12 1.24x, tai12a 1.20x, ...). Valid
throughout; the cause is the order in which incumbents are found: a dropped node holds no optimum, but it can
hold the good solutions the key-off search would have found early and fathomed with. From one above the
optimum no instance has more nodes with the key on.

**Cost of the test.** In the solver's code on tai60b's trace (every pair, no early exit, `-O2`): 64 s for
331,154 nodes, 0.19 ms a node, against 39 s of bound a node [m]. On QPB-only instances, where a node costs
tens of microseconds, it can show: esc16a 327 s off, 392 s on with 3% fewer nodes; tai15a 21.6 / 22.6 s
[m, shared machine]. The code allocates two vectors per pair; it could reuse them, but speed was not the brief.
